## Repair, recycle, reconnect

Device owners need a way to find repair help or move unwanted equipment to someone who can reuse it. RECYX combines a marketplace, technician directory, and recycling-facility map for Rwanda, with separate workflows for citizens, technicians, recyclers, buyers, and administrators.

This was a team project at African Leadership University. My documented contribution was backend development: FastAPI REST APIs, JWT authentication with refresh tokens, and routers for listings, technicians, and transactions. Frontend development, database design, deployment, testing, and outreach were shared across other team roles.

## An offer has a lifecycle

The transaction service checks that a listing is available and prevents buyers from making an offer on their own listing. Creating an offer records the buyer, seller, and price, then marks the listing as transacting.

Status updates check that the caller is a party to the transaction. The workflow moves from `offer_received` to `offer_accepted`, then `in_transit` and `completed`, with cancellation available before completion.

<Decision title="Put legal transitions in one place">
  A central transition map defines which status changes the service permits.
  Completed and cancelled transactions have no outgoing transitions, and invalid
  changes receive a validation error. Keeping this rule in the service makes it
  apply independently of which interface sends the request.
</Decision>

## Backend contribution

FastAPI handles the HTTP layer, Pydantic defines request and response shapes, and SQLAlchemy persists application records. JWT authentication and role checks support the different participant workflows. The repository provides SQLite for local development and documents PostgreSQL for deployment.

The broader React application brings these services together through listing discovery, technician search, moderation, and transaction history. That product context explains the API design while keeping my contribution distinct from the team's combined work.

## Evidence and limits

The source includes the transaction service, its allowed-transition map, and tests targeting that map. The repository contribution section separately documents each team member's responsibilities.

The published demo is described in the repository as an interface with demo data; full backend functionality requires local setup. The transaction service handles offer coordination and status tracking. Concurrent inventory reservation and payment settlement would require additional implementation and validation.
